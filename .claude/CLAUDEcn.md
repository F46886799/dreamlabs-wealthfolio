## 项目概述

Wealthfolio - 本地优先数据的桌面投资跟踪器。React + Vite 前端，Tauri/Rust 后端，SQLite 存储。

关键目录：

- `apps/frontend/` — React 应用（页面、组件、命令、钩子）
- `apps/tauri/` — Tauri 桌面/移动应用（IPC 命令）
- `apps/server/` — Axum HTTP 服务器（Web 模式）
- `crates/` — Rust crates（核心逻辑、存储、市场数据、连接、设备同步）
- `packages/` — 共享 TS 包（addon-sdk、ui、addon-dev-tools）
- `addons/` — 可分发的插件

## 快速命令

- 桌面开发：`pnpm tauri dev`
- Web 开发：`pnpm run dev:web`
- 测试：`pnpm test` | `cargo test`
- 类型检查：`pnpm type-check`
- Lint：`pnpm lint`

## 行为准则

**权衡：** 这些准则倾向于谨慎而非速度。对于琐碎的任务，请使用判断力。

### 1. 编码前思考

**不要假设。不要隐藏困惑。揭示权衡。**

在实施之前：

- 明确陈述您的假设。如果不确定，请询问。
- 如果存在多种解释，请呈现它们——不要默默选择。
- 如果存在更简单的方法，请说出来。在必要时反对。
- 如果有些东西不清楚，请停下来。说出令人困惑的地方。询问。

### 2. 简单优先

**解决问题的最少代码。没有投机性的东西。**

- 不要超出要求的功能。
- 不要为单次使用的代码创建抽象。
- 不要创建未请求的"灵活性"或"可配置性"。
- 不要为不可能的场景处理错误。
- 如果您写了 200 行，但可以是 50 行，请重写它。

问自己："资深工程师会说这太复杂了吗？"如果是，请简化。

### 3. 精准修改

**只触及必须的内容。只清理自己的混乱。**

编辑现有代码时：

- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有问题的东西。
- 匹配现有风格，即使您会以不同的方式做。
- 如果您注意到不相关的死代码，请提及它——不要删除它。

当您的更改创建孤立项时：

- 删除您的更改使其未使用的导入/变量/函数。
- 不要删除预先存在的死代码，除非被要求。

测试：每个更改的行都应该直接追溯到用户的请求。

### 4. 目标驱动执行

**定义成功标准。循环直到验证。**

将任务转化为可验证的目标：

- "添加验证" → "为无效输入编写测试，然后使其通过"
- "修复错误" → "编写一个重现它的测试，然后使其通过"
- "重构 X" → "确保测试在之前和之后都通过"

对于多步骤任务，陈述一个简要的计划：

```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]
```

强大的成功标准让您独立循环。弱标准（"让它工作"）需要不断澄清。

---

**这些准则有效，如果：** 差异中的不必要更改更少，由于过度复杂而导致的重写更少，澄清问题在实施之前而不是在错误之后出现。
